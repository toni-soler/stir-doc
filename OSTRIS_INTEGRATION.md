# STIR ↔ osTRIS integration

## IMPLEMENTED NOW (public osTRIS 0.3, extended for STIR 0.3)

Verified against [public osTRIS](https://github.com/toni-soler/ostris) commit d92aa1f605884ebdcd8e97fff46f4067b0416bcc, extended in the same repository with the discovery/provisioning/status surface below: TransactionController, ProposalAuthorizationService, CommitReceipt, DiscoveryController/DiscoveryService, ProvisioningController/ProvisioningService and CORE_WIRE_AND_DECISION_SEMANTICS_V0_1.md.

STIR 0.3's gap analysis (below, previously "PROPOSED / FUTURE") found osTRIS had no public discovery, provisioning or transaction-status endpoints - the previous integration could create proposals but never read anything back or provision the objects a proposal needs. Since STIR "nunca accede directamente a tablas osTRIS" and no workaround was acceptable, osTRIS itself gained a minimal, documented surface for this (`docs/specification/PUBLIC_APPLICATION_API_V1.md`, implementation-level, explicitly non-normative): read-only discovery (`GET /api/ostris/communities/**`, permission `OSTRIS_DISCOVERY_READ`), provisioning (`POST /api/ostris/communities`, `.../units`, `.../participants/activate`; permissions `OSTRIS_COMMUNITY_MANAGE`/`OSTRIS_PARTICIPANT_ACTIVATE`) and a transaction-status read (`GET /api/ostris/transactions/{id}`, permission `OSTRIS_TRANSACTION_READ`). Every object provisioning creates already existed as a normative osTRIS concept (Community, UnitOfAccount, Participant, Account, Credential, ProtocolController, AccountControlPolicy) - this only exposes their creation, using UuidV7 identifiers and `activation_sequence=0` (active before any transaction ever commits), exactly as osTRIS's own existing test fixtures already did by hand. No normative osTRIS semantics changed: credit-floor enforcement, threshold authorization, the AuthorizationPayload wire format and the "a failed commit leaves the proposal PROPOSED forever" rule are all unchanged.

| POST /api/ostris/transactions/proposals | communityId, unitId, transactionId, purpose, entries[{accountId,amount}], references, optional contractualMetadataDigest, resolutionBasisType, resolutionBasisId |
| POST /api/ostris/transactions/{id}/authorizations | accountId, credentialId, signatureBase64url |
| POST /api/ostris/transactions/{id}/governance-authorizations | authorityId, authorityPolicyVersion, resolutionBasisType, resolutionBasisId, coveredAccounts, credentialId, signatureBase64url |
| POST /api/ostris/transactions/{id}/commit | Receipt: transactionId, communitySequence, protocolDigest, committedAt |
| GET /api/ostris/transactions/{id} | Status: transactionId, communityId, unitId, purpose, wireFormat, ostrisCoreVersion, authorizationPayload (exact canonical bytes to sign), authorizationDigest, status, committedSequence, protocolDigest, committedAt, authorizedAccountIds |
| GET /api/ostris/communities/{id}, .../units/{id}, .../accounts/{id}, .../credentials/{id} | Read-only discovery: name/code/scale/balanceProjection/creditFloor/riskState etc., never RiskSubject/IdentityAssurance/Finding internals or private keys |
| POST /api/ostris/communities, .../{community}/units | Provisioning: name -> communityId; code+scale -> unitId (rare, tenant-level) |
| POST /api/ostris/communities/{community}/participants/activate | Provisioning: displayName, unitId, publicKeyBase64url (client-generated, 32 raw bytes base64url), optional creditFloor -> participantId/accountId/controllerId/credentialId + a 1-of-1 AccountControlPolicy naming that controller the account's sole authorizer (routine, per user) |

Permissions: OSTRIS_TRANSACTION_CREATE, OSTRIS_TRANSACTION_AUTHORIZE, OSTRIS_TRANSACTION_COMMIT, OSTRIS_TRANSACTION_READ, OSTRIS_DISCOVERY_READ, OSTRIS_COMMUNITY_MANAGE, OSTRIS_PARTICIPANT_ACTIVATE. Proposal response: transactionId, authorizationDigest, status. Economic IDs obey UUIDv7; amounts are signed integer minor-unit strings. Application 0.3.0 retains normative OSTRIS-CORE-JCS-1 / ostrisCoreVersion 0.1.

Because STIR relays the CALLER'S OWN bearer token to every one of these endpoints (never a separate service credential - see ARCHITECTURE.md), osTRIS's `@PreAuthorize` checks run against that same caller's IDAX tenant role: a STIR tenant role that should be able to activate economic exchange needs these osTRIS-side permission codes granted alongside the `stir.economic.*` ones, not just the STIR-side ones.

Account authorization is Ed25519 evidence checked against effective AccountControlPolicy and credential/controller bindings. Shell login is not this signature. Governance cannot substitute ordinary EXCHANGE authorization. Commit evaluates policies and writes the journal. Reusing a transaction ID with different intent is rejected.

contractualMetadataDigest is optional lowercase SHA-256 hex in participant authorization. references permits only purpose-defined keys: do not invent listingId/tradeId keys. Ordinary EXCHANGE starts with {}; STIR retains its transaction mapping.

## IMPLEMENTED IN 0.3: real economic exchange

STIR does not modify osTRIS balances or economic state directly - every economic state transition happens through the normative osTRIS transaction lifecycle above, called server-to-server from `OstrisClient` (stir-backend). STIR commercial data never becomes osTRIS journal data except the AgreementSnapshot's SHA-256 digest (`contractualMetadataDigest`) - descriptions, messages and bios never leave STIR.

Explicit tenant/marketplace -> community and tenant/user -> participant bindings (`MarketplaceEconomicBinding`/`ParticipantEconomicBinding`, see DOMAIN_MODEL.md) are never inferred from UUID equality; they are created once, by an explicit bootstrap/activate action, and read back through the discovery endpoints above.

AgreementSnapshot canonicalization (`AgreementSnapshotService`/`CanonicalJson`, stir-backend) is RFC 8785 JCS (`io.github.erdtman:java-json-canonicalization` on the Java side, matching the `canonicalize` npm package on the JS side - the same library osTRIS's own reference implementation already cross-checks against Node's `canonicalize` in its node-vector verifier). Format identifier `STIR-AGREEMENT-JCS-1`, schemaVersion 2: `{format, schemaVersion, agreementId, negotiationId, listingId, listingDirection, initiatorId, ownerId, acceptedOfferId, message, quantity, unitLabel, proposedAmount, proposedUnitRef, terms, payerUserId, payeeUserId, acceptedAt, nonce}`. `digestSha256 = SHA-256(canonical bytes)`; `CanonicalJsonTest` (Java) and `canonical-json.test.mjs` (JS) share a test vector proving both implementations produce byte-identical output for the same input. The two Agreement parties can read `canonicalJson`/`digestSha256`/`schemaVersion`; nobody else can reach the Agreement at all (404).

`TradeService.activate()` proposes the osTRIS EXCHANGE with `contractualMetadataDigest` set to exactly this AgreementSnapshot digest - never recomputed or approximated. Client-side Ed25519 signing (`src/signer.js`, stir-frontend): keys are generated with WebCrypto (`crypto.subtle.generateKey`, non-extractable where the platform allows) and persisted per-tenant-per-user as a live `CryptoKeyPair` in that browser's own IndexedDB - never exported as raw bytes, never sent to STIR or osTRIS. The client never reconstructs osTRIS's normative AuthorizationPayload itself: it signs the exact `authorizationPayload` text osTRIS hands back from `GET .../trade/signing-payload`, prefixed with the domain separator `"OSTRIS:TX:AUTH:V1" + 0x00` exactly as CORE_WIRE_AND_DECISION_SEMANTICS_V0_1.md specifies.

Timeout means unknown/pending, never success - `TradeService.sync()` reconciles by independently re-reading osTRIS's own transaction status (never trusting a client's claim of success). A directly-observed commit failure (e.g. a credit-floor breach) marks the Trade REJECTED; STIR never fabricates that status from anything else, since osTRIS itself never persists a "REJECTED" proposal status (a failed commit leaves the proposal PROPOSED forever, per CORE_WIRE_AND_DECISION_SEMANTICS_V0_1.md). Activate/commit are idempotent.

Ledger already anchors committed osTRIS proofs through its outbox/HTTP adapter. STIR does not reproduce proof generation or anchor logic. Anchor and COMMITTED remain separate.

Deferred: multi-credential rotation, RiskSubject/IdentityAssurance and governed multi-controller policies (osTRIS's provisioning convenience surface intentionally excludes these - a caller needing them provisions directly against the normative tables/future richer endpoints); a non-WebCrypto signing fallback (not needed - WebCrypto Ed25519 is available on every STIR deployment's real origin, confirmed empirically).
