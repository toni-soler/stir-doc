## Runtime proof semantics

Core's public tenant_create database capability provisions fixture tenants because Shell has no public tenant-creation HTTP route. User, role, permission and role-assignment fixtures use public Shell HTTP only. No direct Core table inserts/updates or economic fixtures are used. Test passwords remain in memory; local evidence files contain fixture identifiers only.

The A/B test checks both tenants symmetrically, own update, foreign UUID read/update/close, foreign tenant path, contradictory X-Tenant, and combined text/category/resourceKind/status filters. Runtime SQL records session identity, role attributes/memberships, enabled/forced RLS and policy expressions. Both idax_app and idax_admin see only the transaction-local tenant; no tenant context sees zero rows. This is executed against the actual deployed database, independently of Testcontainers.

## Earlier failures resolved before the final clean run

The initial direct TokenValidator adapter allowed login but failed authenticated catalogs (403); delegating Core JwtAuthFilter fixed this through the public authentication contract. Initial A/B fixture setup omitted separate role-permission/user-role calls; the corrected fixture uses those actual public routes and passes. A previous Docker attempt hit transient registry/Alpine network failures; unnecessary curl installation was removed in favor of wget already in the runtime image. An audit false positive on the public /roles/users/ endpoint was corrected to distinguish an API path from a filesystem home path. The browser test initially used exact label matching on wrapped selects; matching the actual accessible label fixed the test without changing application UI.

The public-source Shell adapter remains explicitly temporary. Its fix belongs to idax-shell, commit afb3dce1ef7d6f722f18f804bb1f70f48687168c, branch codex/public-extension-contract. No push, tag, release or production deployment occurred.

## Bugs found and fixed during 0.3 validation

None of these were pre-existing 0.2 regressions; all were introduced by 0.3 work and caught by validation before this PASS, not after:

- `agreement_payer_not_payee` CHECK constraint used `payer_user_id IS DISTINCT FROM payee_user_id`, but SQL treats two NULLs as NOT distinct - this rejected the legitimate NOT_APPLICABLE case (both NULL) along with the real bug it was meant to catch. Fixed to `payer_user_id IS NULL OR payer_user_id IS DISTINCT FROM payee_user_id`.
- `OstrisClient.post()` never called a terminal method on Spring's `RestClient` `ResponseSpec` for `Void`-typed (bodiless) responses - so `retrieve()`'s default error handling never ran and a 4xx/5xx from osTRIS's authorization endpoint passed silently as "success". Fixed to always call a terminal method (`toBodilessEntity()`/`toEntity()`).
- `TradeService.commit()`'s catch block wrote the REJECTED status and then rethrew, inside a class-level `@Transactional` method - Spring rolled the whole transaction back on the way out, silently undoing the REJECTED write. Fixed by recording it through a separate `@Transactional(REQUIRES_NEW)` bean (`TradeRejectionRecorder`), so the write survives.
- `economic.jsx` treated `EconomicActivationService.marketplace()`'s "not yet bound" response as 404, but the backend actually returns 409 - the UI showed "Loading..." forever instead of the bootstrap form. Fixed the status check.
- `api.js`'s generic request helper fell back to `{}` when a response body failed to parse as JSON, which is exactly what a 200-with-empty-body response does (Spring writes nothing for a `null` controller return value) - `TradeStatus`'s `trade === null` check never matched, so the "not yet activated" UI never showed. Fixed to parse an empty body as `null`.

## Earlier failures resolved before this PASS

A new locale key named `community` (the osTRIS economic community) collided with the pre-existing `community` catalog-code translation key; caught via `npm run build`'s esbuild duplicate-key warnings (not by the user), renamed to `economicCommunity`. Two browser-script bugs were self-caught before their first real run: an ambiguous `get_by_text("Confirmado")` assertion (both the Agreement page's economicPhase badge and TradeStatus's own badge can read "Confirmado") fixed by asserting on the unique receipt-only "Secuencia de la comunidad" text; and every `withNav`-wrapped page (listing/negotiation/agreement/profile detail) renders only a single "← Marketplace" back button, never the full tab bar - navigation steps that follow such a page now go through that back button first. `get_by_label` was unreliable for a `<select>` wrapped in a `<label>` in this Chromium/Playwright combination (it worked for `<input>`); switched to `get_by_role("combobox", ...)`, the more idiomatic Playwright pattern for `<select>` elements anyway.

## Bugs found and fixed during 0.4 validation

All caught by validation before this PASS, not after - none of these reached a committed "done" state without being found first:

- **(Most significant.)** `TradeService.authorize()` relayed `ParticipantEconomicBinding.credentialId` - fixed permanently at the user's FIRST activation - to osTRIS's signature verification, regardless of which device actually produced the signature being submitted. A second (or later) device's perfectly valid signature always failed osTRIS's own verification (`INVALID_SIGNATURE: Invalid account signature`), because STIR told osTRIS to check it against the wrong - and, after that first device's credential is revoked, no-longer-even-valid - public key. This made the entire multi-device feature non-functional for its actual purpose (completing a real exchange from an added device) despite every other part of the device lifecycle (add, list, revoke, self-lockout guard) working correctly and passing its own tests. Root-caused only by adding a live Playwright network interceptor on the `/trade/commit` response and reading osTRIS's real rejection reason. Fixed by having the caller's own client supply which `credentialId` it signed with (`POST .../trade/authorizations` now requires it); STIR never itself verifies a signature either way, so nothing about the trust model changed - osTRIS remains the sole verifier. `economic_exchange_e2e.py` (0.3) needed a matching update, since it now must supply `credentialId` too; this is an intentional API contract change, not a regression, and was caught immediately by that existing 0.3 script.
- `DeviceCredentialService.revokeDevice()` looked up the credential in STIR's own local `participant_device_credential` friendly-label table, which only ever gets a row through the explicit "add device" flow - the FIRST device (bound during `activate()`, never through `addDevice()`) has no such row and could never actually be revoked, even though the UI presented a fully-functional-looking "Revocar" button for it that always 404'd. Fixed to authorize the revoke via osTRIS's own controller/credential discovery - the same source of truth `myDevices()` already used for active/revoked - instead of the local label table.
- `Marketplace()`'s `onCancel` handler for `ListingEditor` never bumped `revision`, so a photo uploaded during an edit session (a separate, immediate API call - not deferred to "Guardar") never appeared in the card grid unless the user happened to click "Guardar" instead of "Cancelar" to leave; the grid silently kept showing stale pre-photo data. Fixed by bumping `revision` in both `onCancel` and `onSaved`.
- `stir.http404`/`stir.http409`, the frontend's generic per-status fallback error texts, were hardcoded to Listing-specific wording ("Listing not found.", "This listing changed or was closed. Reload before editing.") but are shown for ANY unmapped 404/409 anywhere in the app - a plain 409 from `EconomicActivationService.activate()` (profile not set up yet) showed the wrong, actively misleading Listing-specific message on the economic activation screen, violating section 13's plain-language-error requirement. Fixed the two generic fallbacks to be context-neutral, and gave that specific activation conflict its own `PROFILE_REQUIRED_BEFORE_ACTIVATION` code, following the same `CODE: detail` convention already established for `CREDIT_FLOOR_EXCEEDED`.
- The moderation nav link was initially gated on the IDAX Shell module SDK's `useAuth().hasPermission()`. At the time this read as a stale-cache problem specific to custom tenant roles; 0.5's investigation found the real cause in the actual public `idax-shell` repository (not the private internal admin frontend this diagnosis was first made against, which STIR never actually loads at runtime): Shell's own `Session.user` record had no `permissions` field AT ALL, so `hasPermission()` returned false for every non-superuser account, for every permission, unconditionally - see this file's 0.5 section for the real fix. STIR's own workaround still stands and is still exercised by `moderation_browser_smoke.py`: a minimal, STIR-owned, no-op `GET .../moderation/access` probe (a 200 IS the answer; `@PreAuthorize` does the real check) that the frontend calls once instead of depending on the platform's own client-side permission signal - kept intentionally even after the Shell fix, since a module's frontend should not have to assume every deployment is running a patched Shell.
- `restore.py`'s raw Docker-volume-level restore of the MinIO data directory left the already-running MinIO container's in-memory view of the bucket stale, causing a transient `Resource requested is unreadable, please reduce your request rate` error on the very first reads immediately after restore - discovered during the actually-executed backup/restore drill above. Fixed by having `restore.py` restart the `minio` service as its own final step.
- `DeviceCredentialService.myDevices()`'s fallback label for a credential with no local friendly-label row was the hardcoded English string `"Device"`, bypassing i18n entirely regardless of the viewer's own locale. Fixed to return `null` and let the frontend supply a properly translated `unnamedDevice` fallback.
- Four `<img>` elements (the Listing photo gallery, both the "my profile" and public-profile avatar renderers, the photo-upload preview grid) had `alt=""` despite being meaningful, non-decorative content - a screen-reader user got zero information about a Listing's own photos or a person's avatar. Fixed with real, context-specific alt text.

Test-authoring bugs (mine, not the application's), caught before or during the first real run of each script: `credential_device_lifecycle_browser_smoke.py` initially skipped the "Mi perfil" setup step Ana needs before activation is possible (a genuine backend precondition, not a bug) and, after `.reload()`, tried to re-click a "Activación económica" tab button that does not exist on that `withNav` detail route (only "Resumen"/"← Marketplace" do); `moderation_browser_smoke.py`'s reporter-role fixture initially granted no `stir.content.report` at all, which would have made the report step itself impossible rather than testing least-privilege; `public_pilot_browser_smoke.py`'s locator for the just-uploaded thumbnail assumed a "← Marketplace" button exists on `ListingEditor` (it is rendered inline inside `Marketplace` itself, with only its own "Cancelar"), and its Home-dashboard assertion needed `.first` once the same Listing legitimately appears in two sections of that page.
